    BrowseComp-Plus

    Run Pocket Context Agent on BrowseComp-Plus, a research benchmark with 830 questions and a fixed corpus of 100,195 documents. This integration uses the official Lucene BM25 index and exports the files expected by the upstream evaluator. It runs this repository's agent and context tools, so its trajectories differ from the upstream baseline agents. For matched Pocket Context, ReAct, ReSum, and ACM experiments, see Context-method comparison.

    Install and prepare

    Use Python 3.11 and Java 21 with java on your PATH. Set JAVA_HOME to your Java 21 installation if your machine has several Java versions. BM25 inference runs on CPU; running the official Qwen3-32B judge requires a separate Linux GPU environment.

    uv venv --python 3.11
uv pip install --python .venv/bin/python -e '.[browsecomp-plus]'
source .venv/bin/activate
mini-extra browsecomp-plus prepare

    Preparation streams only question IDs, questions, and reference answers from the pinned dataset revision, decrypts them locally, and downloads the official BM25 index (about 2.2 GB). The reference answers are for evaluation and are never included in the agent's task or observations. Hugging Face access is public; HF_TOKEN is optional for higher download rate limits. Model inference requires your provider's credentials, such as DEEPSEEK_API_KEY, OPENAI_API_KEY, ANTHROPIC_API_KEY, or OPENROUTER_API_KEY. Export credentials in your shell, put them in the repository's ignored .env, or use the existing mini-extra config global configuration. Keep credentials out of YAML overrides because run configurations are saved.

    Files go under the ignored data/browsecomp-plus/ directory. Use prepare --no-index to prepare only questions, or --data-dir PATH to choose another location. For a cache inside the ignored data directory, set HF_HOME="$PWD/data/browsecomp-plus/.cache" before preparation. Keep decrypted questions, reference answers, and trajectories private to avoid benchmark contamination. Add equivalent ignore rules if you choose other data or output directories.

    Run

    Reserve the exact 150 evaluation questions published with the implementation paper:

    mini-extra browsecomp-plus reserve

    The IDs come from the authors' bcp_eval_150.json at revision f06f90e728af8580a4515812425c1620144145a2 of agentic-context-management. This writes ignored eval150.jsonl and development680.jsonl files. Both local and Daytona runs select development680 by default, keeping the 150 evaluation questions out of smoke tests. Use --split eval150 explicitly when ready to evaluate.

    Start with one question using your configured default model:

    mini-extra browsecomp-plus run --limit 1 \
  --output runs/browsecomp-plus/smoke \
  -c agent.step_limit=10 \
  -c agent.cost_limit=0.25

    Then run the development set with an explicit provider/model name:

    mini-extra browsecomp-plus run --model PROVIDER/MODEL \
  --workers 4 --output runs/browsecomp-plus/my-model

    The default limits are 100 model calls, $3, and 1,800 seconds per question. The cost and time limits are checked between calls and can be exceeded by an in-flight call; they are stopping thresholds rather than hard billing caps. Four workers can have four requests in flight, and a full benchmark can be expensive. Override settings with repeatable -c options accepting YAML files or key=value values. For example, -c model.model_kwargs.reasoning_effort='"high"' passes a provider setting, and --model-class openrouter selects another existing model interface. Use a separate output directory for each model, configuration, dataset, or index.

    The corpus interface accepts search QUERY, get_document DOCID, and submit FINAL RESPONSE through the existing bash tool. These commands do not execute a shell or provide access to the live web, local files, reference answers, or credentials. Search returns five full documents by default, matching the upstream untruncated BM25 setting. Use -c environment.k=10 or -c environment.snippet_chars=4000 to change retrieval settings, and report those changes when comparing results. Snippet truncation uses characters; zero keeps full text. Document lookups return the full document unless a token cap is configured. The existing compact_block and expand_block tools remain available for context management.

    Direct DeepSeek API

    Set DEEPSEEK_API_KEY in your shell or the ignored .env, then select the direct-provider profile:

    mini-extra browsecomp-plus run --method pocket_context --limit 1 \
  -c browsecomp_plus_deepseek \
  --output runs/browsecomp-plus/deepseek-smoke/pocket_context

    This uses deepseek/deepseek-flash through LiteLLM at https://api.deepseek.com, with thinking enabled and high effort. It does not use OpenRouter or serve the Qwen model. The profile keeps a 128,000-token experimental window, 100 main calls, 16,384 maximum output tokens, a $0.50 stopping threshold, and a 30-minute task timeout. It uses ten BM25 results, 512/128-token new/seen previews and an 8,192-token document cap. The Qwen corpus tokenizer remains fixed for retrieval consistency; context counts are estimates, not DeepSeek's exact chat-template tokenization.

    Apply the same profile to react, resum and acm; see Context-method comparison. Do not layer this profile on top of the OpenRouter profile or reuse its output directories. API keys stay out of the YAML and saved manifests. For Daytona, use create --provider-key DEEPSEEK_API_KEY with the matched daytona matrix workflow below; the legacy single-provider daytona run remains OpenRouter-only. These commands incur DeepSeek model charges, but merely loading or validating the configuration does not call the API.

    Muse Spark 1.3 Contributor (Meta direct)

    Set META_API_KEY in your shell or ignored .env, then select the exact Contributor profile:

    mini-extra browsecomp-plus run --method pocket_context --split development680 --limit 1 \
  -c browsecomp_plus_muse_spark_1_3_contributor \
  --output runs/browsecomp-plus/muse-1.3-contributor-smoke/pocket_context

    The model is explicitly meta/muse-spark-1.3-contributor, not Standard muse-spark-1.3 or Contributor 1.2. The profile uses the direct endpoint https://api.meta.ai/v1 and LiteLLM's native Responses interface, with encrypted reasoning replay, optional readable reasoning summaries, high effort, and no server-managed response storage. Contributor does not support max effort. It retains the shared 128,000-token experimental cap and corpus/budget settings, and requires no OpenRouter key. Use fresh output directories and the same profile for every method; do not merge it with another provider's profile. For Daytona, create a fresh pool with --provider-key META_API_KEY and use daytona matrix -c browsecomp_plus_muse_spark_1_3_contributor. The legacy single-provider daytona run does not support Meta credentials.

    Contributor permits Meta to use prompts and responses for model training. This includes submitted benchmark context; store: false does not opt out of Contributor data use. Check your benchmark/data policy before launching held-out tasks. See Meta's Contributor terms and the comparison guide. No inference runs are launched by loading this profile.

    OpenRouter and the paper settings

    Copy .env.example to .env and supply OPENROUTER_API_KEY and, for cloud workers, DAYTONA_API_KEY. The provided profile selects qwen/qwen3.5-9b through OpenRouter with Together as the only allowed provider and provider fallbacks disabled:

    mini-extra browsecomp-plus run --limit 1 \
  -c browsecomp_plus_openrouter \
  --output runs/browsecomp-plus/openrouter

    The profile allows research tool calls or a final text response in the benchmark answer format. This profile uses ten BM25 results, Qwen tokenizer previews of 512 tokens for new documents and 128 for previously retrieved documents, and an 8,192-token document cap. It sets a 128,000-token context window, 100 model calls, a $0.50 stopping threshold per task, and a 30-minute task timeout. The last tool result of each turn receives a [CURRENT CONTEXT TOKEN: N] marker estimating the active conversation plus the next response's maximum output allowance. Estimates use the configured corpus tokenizer when available, otherwise four UTF-8 bytes per token, and include message framing and tool schemas. Encrypted reasoning payloads are excluded from text tokenization; retained reasoning is counted using provider-reported reasoning usage, falling back conservatively to reported output usage when the reasoning breakdown is unavailable. At 95% of the projected window, the agent receives a stop instruction, makes one text-only final generation, and ends without executing further tools. Oversized new tool results are visibly truncated before entering the conversation so there is room for the final generation; complete raw tool output remains in trajectory metadata. The response allowance is capped to the estimated remaining space. An initial task or model response that already exceeds the window ends with LimitsExceeded. Search results distinguish new documents, previously seen evidence still in context, and compacted evidence with archive tags for expand_block. The agent is instructed to read a document before answering, corroborate uncertain candidates, and use Pocket Context's own memory tools. The cost threshold is checked between calls and can be exceeded by an in-flight request. Ten concurrent tasks can therefore consume roughly ten times the per-task threshold.

    This is a paper-guided retrieval configuration for this repository's existing agent. Its compact_block selects bounds for a separate same-model compaction agent, and expand_block retrieves the local archive. The compaction agent sees only the active history prefix through the selected end. These tools differ from the paper's memory pipeline, and the profile does not reproduce the paper's trained policy. The model decides whether context tools are useful; a short successful episode can use neither.

    Ten parallel Daytona workers

    Daytona is optional for local corpus retrieval. The legacy single-provider daytona run launcher remains OpenRouter-only and supports at most 10 workers. It uses one active task per sandbox and shares a snapshot containing Java 21, CPU dependencies, the pinned BM25 index, and the Qwen tokenizer. daytona create --workers supports pools of up to 120 workers, with at most 10 sandbox startups in flight; larger pools are for the matrix workflow below, not increased legacy run concurrency.

    uv pip install --python .venv/bin/python -e '.[browsecomp-plus,daytona]'
mini-extra browsecomp-plus daytona snapshot --name pocket-browsecomp-plus
mini-extra browsecomp-plus daytona create --snapshot pocket-browsecomp-plus --workers 10
mini-extra browsecomp-plus daytona check
mini-extra browsecomp-plus daytona run --workers 10 --limit 20 --success-limit 20 --cleanup

    check verifies real corpus retrieval and tokenizer loading in every worker without model calls. The launcher sets JAVA_HOME before loading Pyjnius, including on snapshots with only a Java runtime. The application wheel is installed separately from the shared snapshot. Only the selected task ID, question, and configuration are uploaded for each task; reference answers and the Daytona key stay off the workers. The OpenRouter key is supplied through sandbox environment variables and is never baked into the snapshot.

    --limit bounds attempted tasks; --success-limit stops after the requested number of submissions without scheduling excess concurrent tasks. Twenty attempts may produce fewer than twenty submissions if tasks hit limits or fail. A completed submission does not establish answer correctness; correctness still requires the judge below. By default, local outputs use a temporary directory and are deleted after the summary is printed. Remote task workspaces and process sessions are always removed, including on failure. The reusable corpus snapshot and worker pool remain available, with workers configured to stop and delete after 30 idle minutes. Use daytona status to inspect workers and daytona delete to delete the pool explicitly.

    To preserve trajectories for an evaluation run, select the held-out split explicitly and opt into artifacts:

    mini-extra browsecomp-plus daytona run --workers 10 --split eval150 --limit 150 \
  --keep-artifacts --output runs/browsecomp-plus/eval150

    The pool manifest is ignored at data/browsecomp-plus/daytona-pool.json. Create a fresh pool after application or credential changes or after idle deletion.

    Matched Daytona matrix

    daytona matrix runs Pocket Context, ReAct, ReSum and ACM concurrently with dedicated sandboxes per method and one active question per sandbox. --workers-per-method defaults to 1, preserving sequential processing within each method. Effective workers per method are min(requested workers per method, selected question count); the pool needs four times that many distinct workers. Methods never share workers or oversubscribe sandboxes. Each method's dynamic queue assigns the next selected question to a free worker, retaining failed attempts without retries or dropping failures. Use a separate --pool manifest and a fresh pool containing the updated application:

    mini-extra browsecomp-plus daytona create \
  --snapshot pocket-browsecomp-plus --workers 4 \
  --provider-key DEEPSEEK_API_KEY \
  --pool data/browsecomp-plus/daytona-matrix-pool.json
mini-extra browsecomp-plus daytona check \
  --pool data/browsecomp-plus/daytona-matrix-pool.json
mini-extra browsecomp-plus daytona matrix \
  --pool data/browsecomp-plus/daytona-matrix-pool.json \
  --split eval150 --limit 1 --seed 42 -c browsecomp_plus_deepseek \
  --output runs/browsecomp-plus/matched-smoke --dry-run

    create --provider-key forwards only the named key, defaulting to OPENROUTER_API_KEY. Any key name ending in _API_KEY is allowed except DAYTONA_API_KEY; the Daytona credential is never forwarded. Match the key to the matrix's provider profile and recreate the pool when changing it. Matrix uses the DeepSeek profile by default if no -c is supplied. Explicit configs replace the default provider profile; the base configuration is always applied. Do not merge provider profiles.

    Repeat --query-id ID for explicit selection (use --limit 0 to run all specified IDs); --limit 0 without IDs selects the whole split. --seed N samples reproducibly without replacement; otherwise selection follows dataset order. The shared cohort is randomized once, not separately per method or worker. The parent selection.yaml records the shared IDs, seed, requested workers_per_method, effective workers per method and per-method sandbox lists. Matrix requires a new or empty output directory, with no hidden resampling or resume.

    --dry-run validates selection/configuration without writing files or calling any API. Omit it to launch the paid run:

    mini-extra browsecomp-plus daytona matrix \
  --pool data/browsecomp-plus/daytona-matrix-pool.json \
  --split eval150 --limit 1 --seed 42 -c browsecomp_plus_deepseek \
  --output runs/browsecomp-plus/matched-smoke
mini-extra browsecomp-plus daytona status \
  --pool data/browsecomp-plus/daytona-matrix-pool.json
# After matrix completion:
mini-extra browsecomp-plus compare \
  --runs runs/browsecomp-plus/matched-smoke \
  --output runs/browsecomp-plus/matched-smoke/comparison.yaml

    For a full 30-question cohort with up to 30 dedicated sandboxes per method (120 total):

    mini-extra browsecomp-plus daytona create \
  --snapshot pocket-browsecomp-plus --workers 120 \
  --provider-key DEEPSEEK_API_KEY \
  --pool data/browsecomp-plus/daytona-matrix-120-pool.json
mini-extra browsecomp-plus daytona check \
  --pool data/browsecomp-plus/daytona-matrix-120-pool.json
mini-extra browsecomp-plus daytona matrix \
  --pool data/browsecomp-plus/daytona-matrix-120-pool.json \
  --workers-per-method 30 --split eval150 --limit 30 --seed 42 \
  -c browsecomp_plus_deepseek \
  --output runs/browsecomp-plus/matched-30

    The matrix command above launches a paid run; append --dry-run to validate without launching tasks. The 10-at-a-time pool startup limit is not a matrix task-concurrency limit. Fewer questions clamp concurrency: --workers-per-method 30 --limit 10 uses only 10 workers per method, or 40 active task slots, even with a 120-worker pool. Extra sandboxes do not receive duplicate questions.

    Use the existing daytona status command for worker tracking. With one effective worker per method, each method directory keeps its original run.yaml, summary.yaml, root query results and trajectories.tar.gz. Multiworker runs keep each task's original artifacts under METHOD/tasks/QUERY_ID/{run.yaml,QUERY_ID.json,trajectories.tar.gz} and publish parent METHOD/run.yaml, root METHOD/QUERY_ID.json results and METHOD/summary.yaml with the common full-cohort manifest and fingerprint, without rewriting shard provenance. Shared selection metadata and sandbox lists stay in the matrix parent.

    compare still accepts the matrix parent output, and grading still uses the root per-method directories, not task shards. Without judge grades, comparison reports resource usage only, not answer correctness; judge each method separately and supply --grades as described in Context-method comparison.

    The DeepSeek profile's $0.50 threshold is per method per question, including auxiliary inference, and is checked between calls: it is not a hard billing cap. Budget for all four methods' model charges, provider request/token rate limits, Daytona account quotas, infrastructure and any judge costs. The snapshot uses 1 CPU / 4 GB per worker: 120 provisioned sandboxes require 120 CPUs / 480 GB even if fewer tasks are active. Pool creation provisions billable infrastructure; check makes no model calls and matrix --dry-run calls no API. Editing these docs or validating with --dry-run starts no paid run. These examples are instructions, not claims that a run has occurred.

    Local selection and artifacts

    Use repeated --query-id ID, --offset N, and --limit N to select queries in dataset order for the local run command. --queries FILE accepts an alternative decrypted JSONL with query_id and query fields, and --index DIR accepts an alternative Lucene index. Local development runs without --method skip completed queries and retry incomplete queries. Explicit method runs and local eval150 runs retain all recorded attempts, including failures, to avoid retry-until-success bias. Runs reject changed settings in an existing output directory. Use --redo-existing to explicitly replace recorded attempts with the same settings; use fresh directories for independent evaluation repeats. A batch exits with status 1 if any query does not finish by submission, while preserving its failure record and trajectory. Unexpected exceptions preserve the current query's record and propagate to the caller.

    Each run contains:

    run.yaml
summary.yaml
QUERY_ID.json
trajectories/QUERY_ID/trajectory.json
trajectories/QUERY_ID/context.sqlite

    The top-level query files contain query_id, status, tool_call_counts, retrieved_docids, and result, plus model and run metadata. Their metrics include provider-reported peak input tokens, peak input-plus-output tokens, total usage, and semantic tool counts including context tools. The summary reports the maximum input context across all calls, the mean per-task peak, and average tool calls per attempted task. Tool counts include submit; avg_research_tool_calls_per_task excludes it. When a success target is provided, a second summary reports the same metrics for completed submissions only. Retrieval IDs include every document returned by search or successfully fetched directly, even if the agent later compacts the observation. Explicit submissions and final text responses with an extractable Exact Answer: receive status: completed. Results retain the complete response for the official evaluator and also record the last Exact Answer: and Confidence: values, with confidence defaulting to 100 when absent. Budget exhaustion without a final answer remains a failed run for the official evaluator. Trajectories and context archives are kept in subdirectories so the evaluator sees only query results at the run directory's top level.

    Evaluate

    Use the official evaluator rather than a custom answer matcher. Clone its pinned source into the ignored data directory:

    git clone https://github.com/texttron/BrowseComp-Plus.git data/browsecomp-plus/upstream
git -C data/browsecomp-plus/upstream checkout 046949032b0328319cc9a02663a759ec601d9402

    On a Linux GPU machine with enough memory for Qwen3-32B, install the judge in a separate environment and evaluate the exported run directory:

    uv venv --python 3.11 data/browsecomp-plus/judge-venv
uv pip install --python data/browsecomp-plus/judge-venv/bin/python 'vllm>=0.9.0' numpy tqdm
data/browsecomp-plus/judge-venv/bin/python \
  data/browsecomp-plus/upstream/scripts_evaluation/evaluate_run.py \
  --input_dir runs/browsecomp-plus/my-model \
  --ground_truth data/browsecomp-plus/queries.jsonl \
  --qrel_evidence data/browsecomp-plus/upstream/topics-qrels/qrel_evidence.txt \
  --eval_dir runs/browsecomp-plus/evals \
  --tensor_parallel_size 1

    Copy the prepared questions and run outputs to the GPU machine and adjust paths and GPU count as needed. The judge loads Qwen/Qwen3-32B; it does not need a paid model API key. Upstream requests Qwen3-32B judging for leaderboard submissions.

    For an API-based check using GPT-6 Luna, export OPENAI_API_KEY and run our launcher for the upstream alternate judge:

    python -m benchmarks.browsecomp_plus_judge \
  --input-dir runs/browsecomp-plus/my-model \
  --eval-dir runs/browsecomp-plus/evals-gpt-6-luna

    The launcher defaults to gpt-6-luna with an 8,192-token output budget for reasoning and the answer, using the Responses API and the model's default reasoning effort. It preserves the pinned upstream grading prompt and judgment format, including judge model metadata used by compare --grades. Use the same settings for all four methods and a fresh evaluation root when changing judge models or settings: the upstream script otherwise reuses existing judgments. This alternate judge incurs API charges and should be identified separately from the official Qwen judge in reported results.

    Validate the integration

    uv pip install --python .venv/bin/python -e '.[dev,browsecomp-plus]'
pytest -q tests/run/test_browsecomp_plus.py

    These tests create a real Lucene index and run the CLI with the repository's deterministic replay model. They verify retrieval, token caps and markers, document lookup, answer extraction, memory-aware retrieval after compaction and expansion, final-generation steering, usage accounting, held-out partitioning, budget exhaustion, concurrent query isolation, reference-answer isolation, resume behavior, and configuration mismatch rejection without paid API calls.
